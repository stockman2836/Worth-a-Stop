# Worth a Stop

Worth a Stop is a travel planner for people exploring a city on their own. Choose a city and a date to see nearby events, local times, venues and links to the published listings. Explore the map alongside your daily itinerary, add stops and check whether the calculated visits fit your available time. For longer trips, you’ll be able to link days across cities and plan around train journeys, overnight stays, and existing bookings.

## Getting started

You can search for cities by name in the browser or from the command line. Both use the Open-Meteo geocoding API. The command line can also import an organizer’s published event calendar. Run the commands below from the repository root with Node.js 22 or later. Install the dependencies before starting the website, importing events or running the tests.

```sh
npm ci
```

### Website

```sh
node --watch bin/site.mjs
```

Open `http://127.0.0.1:3000` in your browser. The site opens in Russian if your browser language is Russian and in English otherwise. Use the RU/EN switch to change languages. It remembers your choice on this device. An open city keeps its selected date, saved itinerary, preview time, availability filter and active discovery tab across language changes, without needing another city lookup. City and region names follow the geocoder's available translations when you search. Live searches require a connection to Open-Meteo.

Watch mode restarts the development server when its imported backend modules change. Reload the browser after frontend changes. A server started without watch mode must be restarted manually after backend updates; otherwise new frontend files can run against old boundary and place-search logic. For a server without automatic restarts, use `node bin/site.mjs`.

Use the theme button in the header to switch between light and dark appearance. The initial theme follows your system setting; an explicit choice is saved on this device and applied before the page is painted. Changing themes keeps the current map and plan in place. The dark palette covers map tiles, controls, popups, cards and form fields. Theme controls are translated into Russian and English, and the switch still works in the current tab if browser storage is unavailable.

The landing page includes a decorative animated walking route. Cards have brief entrance and hover effects, and adding a stop gives visual feedback alongside the itinerary's status message. Reduced-motion preferences disable decorative motion and limit programmatic map movement. The interface uses local assets and CSS, with no animation library or external UI font dependency. Vector-map glyphs and sprites come from the map provider.

Pick a destination under **Cities with event listings**, or start typing a city name. The destination buttons come from cities with current or upcoming OpenAgenda listings. Suggestions update after a short pause as you type. The country and region help distinguish places with the same name. Select a city to open a workspace with a large map, the daily itinerary alongside it and **Places** / **Events** tabs below the map. **Change city** returns to search. An empty itinerary offers **Explore places** to take you directly to the suggestions.

Set **Date**, **Start at** and the optional **Finish by** in the shared trip bar. Date changes update the agenda, map and saved plan together. The finish limit is saved separately for each city and date. It checks the calculated departure from the final stop and shows remaining minutes or an overrun. An incomplete calculation stays unverified. The limit must be later than the start on the same day, and ambiguous or nonexistent local times require another selection. A return destination is planned.

To build an automatic suggestion, enter both times, select **Relaxed**, **Balanced** or **Active**, then choose **Plan my day**. It uses the live place and event sources for the selected city and date, includes your selected map starting point and checks actual walking legs. With no starting point selected, the walk starts at the first proposed stop. The pace is remembered for the city and preserved across language changes. Visit durations are category-based estimates; published event start and end times are retained.

Under **Your interests**, choose any combination of History, Architecture, Museums, Nature and Art. Leave them empty, or use **Clear selection**, for the original balanced selection. Personal interests are saved on this device across cities and language changes; resetting one city's plans preserves them. If storage is unavailable, choices remain in the current tab with an explicit notice. Changes from another tab update the controls. Changing interests cancels an active calculation and invalidates an unapplied proposal, so an old suggestion cannot be applied under new preferences.

Preferences affect candidate selection before the planner's twelve-place bound and also influence ranking among feasible visits. The initial pool takes up to eight matching objects, balancing straight-line proximity with published prominence, and retains up to four general alternatives, then fills unused slots from the catalogue. With a starting point selected, distances are measured from that point; otherwise published city-centre distances are used. This avoids ignoring a suitable park simply because it appears below the first twelve catalogue entries, or letting small nearby parks displace every prominent one. Opening hours, visit durations, walking limits, event times, the finish deadline and the route-check budget remain in force. Interests are preferences rather than exclusions; when matching places cannot fit, general alternatives can still appear with an explanation.

Each matching suggested stop identifies the selected interests it satisfies. Classification uses mapped place categories; it does not infer a museum's topic from its name or assume that every attraction is historic. An object can match more than one interest without multiplying its preference bonus. Events keep their schedule-based treatment and are not assigned topics by guessing from venue names. A preview still requires **Apply plan** before it replaces the saved itinerary.

The preview lists stop times, source links, estimated visits, walking and waiting minutes, opening-hour checks and variety reasons. Known closed visits, visits crossing a closure, late event arrivals and stops finishing beyond the time window are excluded. Places with unknown opening hours may appear with an explicit check-required label. Events need coordinates and a complete session inside the window; online, cancelled, postponed and sold-out sessions are excluded. Saved place results and incomplete source coverage are identified.

**Preview on map** draws a separate dashed route with orange numbered stops. The saved itinerary remains unchanged until **Apply plan** or **Replace current itinerary**. Applying replaces the whole stop sequence while retaining the selected trip times and starting point. Changes to the date, times, pace, start point or manual stops invalidate the proposal. The apply action also compares the current itinerary with the reviewed snapshot before writing. Cancel discards the proposal, and unapplied previews are not persisted across navigation or language changes. Storage failures keep an applied plan in the current tab and label it unsaved.

The first planner uses a bounded greedy search rather than promising an optimal or exhaustive route. It considers up to twelve places and twelve eligible event sessions, favours verified hours, nearby stops, imminent sessions and category variety, and makes at most 24 distinct walking checks. Relaxed, Balanced and Active cap the plan at four, six and eight stops and individual walking legs at 25, 35 and 45 estimated minutes. Event waiting is limited to one hour. The whole lookup has a 90-second timeout and can be cancelled. Mandatory stops, personal interests, planned meal breaks and a return destination remain future work.

If a search returns no cities, the website checks for nearby spellings in city names and, when needed, asks Wikipedia for a spelling suggestion. It checks the corrected name with the geocoder before showing it. For example, try `Lnodon` or `Будапшт`. Arrow Down moves keyboard focus from the search field to the first result.

Use the **Places** tab to explore named attractions, historic sites, religious landmarks, markets, parks, gardens, viewpoints, museums and galleries across the selected city. There is no 24-place cutoff: all matching public places returned by the city query remain available after deduplication. Coverage still depends on supported categories and published OpenStreetMap data. The search uses the mapped administrative boundary rather than a fixed radius. Places in remote districts can qualify without Wikipedia, Wikidata or heritage annotations. Distances are straight-line estimates from the geocoder's city point to mapped points or area centres. Each name links to its OpenStreetMap object. Opening hours appear as published when available. [© OpenStreetMap contributors](https://www.openstreetmap.org/copyright)

City boundary discovery reads administrative areas and mapped settlement polygons containing the selected geocoder point through Overpass, then matches the GeoNames identifier or published names and translations. When the interface-language name is missing from OSM, it resolves the same GeoNames ID to an English name through Open-Meteo and checks those boundaries again. Conflicting identifiers and equally ranked ambiguous matches are rejected. A verified identity takes priority; otherwise a matching settlement footprint takes priority over surrounding administrative units. Country boundaries qualify only with the explicit OSM `city=yes` designation for a city-state. There is no configured list of city names or landmark IDs. The interface identifies and links the boundary used. Municipal boundaries can include rural districts and exclude neighbouring municipalities or independent enclaves. The enclosed-territory discovery described below supplements the selected city without merging their administrative identities. Compact searches use Overpass area membership; tiled searches check downloaded boundary geometry locally. Displayed centres locate markers. If no matching boundary is available, the interface reports that citywide search is unavailable. [Overpass area queries](https://wiki.openstreetmap.org/wiki/Overpass_API/Overpass_QL#By_area_(area))

If a confirmed settlement footprint returns no matching places after a complete successful query, discovery also checks within 2 km of its centre. This fallback is explicitly labelled **surroundings** beside the map, retains the settlement boundary link, and uses the separate nearby limit of twelve places. It does not narrow a populated city catalogue or activate after a failed city query. Local searches preload named objects in a small box, filter by distance and supply that box to regional source selection. This matters for small footprints such as Nikita, where visitor sites sit outside the mapped settlement polygon.

Results rank places using multilingual names, Wikipedia and Wikidata references, heritage protection and explicit international or landmark annotations. These are prominence estimates from source metadata, rather than an official popularity rating. Distance breaks ties. There are no category quotas or automatic cathedral bonuses. Duplicate names at nearby coordinates and objects sharing a Wikidata identity are combined. Market nodes require additional market tags or a Wikidata reference, and shops tagged as markets are excluded. Replacement searches remain local: up to twelve places within 2 km of the stop.

After the main city loads, discovery can include administrative territories wholly enclosed by its inner boundaries. Every outer boundary way of a candidate must belong to the selected city's inner boundary ways, and its bounds must stay within the city bounds. A neighbouring district sharing only part of the border or a larger surrounding region cannot qualify. Coextensive country and municipal relations are searched once, preferring the country; ambiguous equal-level identities and unsupported nested outer geometry are excluded. These conservative rules use published OSM topology and contain no configured city names, country names or landmark IDs. Compatible boundary mapping is required.

Confirmed enclaves use their own Overpass area membership and the same place categories and prominence rules as the host city. For Rome, this includes Vatican City and its mapped visitor places. Country/territory names, available RU/EN translations, source links and published country codes appear in place cards, map popups and itinerary stops, including saved plans. The original city boundary remains linked, alongside the additional territory boundaries. Identical OSM objects are merged with their territorial attribution preserved. Discovery and loading of additional territories follow the initial city results; an unavailable optional source leaves those results visible and marks the catalogue incomplete. Confirmed enclave discovery is cached for 24 hours. Place-result and boundary cache versions change without deleting saved plans; earlier compatible catalogues remain available as stale fallback during refresh.

Public artworks (`tourism=artwork`) and theatres (`amenity=theatre`) are included when they have a Wikipedia/Wikidata reference or heritage annotation. The evidence restriction is applied both in the source query and when processing records; ordinary named attractions, parks and the existing categories keep their previous eligibility. Documented cultural places named in at least five languages can qualify as highlights, including artworks and theatres. This avoids excluding a prominent installation simply because it is not tagged `tourism=attraction`, while keeping undocumented murals and small venues out of the new categories. Public art uses a palette icon and theatres use a drama icon, with Russian and English labels. A theatre record does not provide a performance time; sessions still come from event sources and opening hours remain unspecified unless published. Compatible earlier catalogues can serve as explicitly stale fallback during a refresh; complete refreshed responses replace them.

Regression fixtures retain the published OSM records for [Zadar's Sea Organ](https://www.openstreetmap.org/way/146457741) and the [Mariupol drama theatre building](https://www.openstreetmap.org/way/1041142766). Tests check category discovery, prominence, overview visibility and translated names without adding city names or object IDs to production rules.

The default **Highlights** list separates the main visitor selection from the full catalogue. Highlight membership uses documented prominence evidence rather than a fixed number of results. The threshold adapts to the strongest documented signals in the city; explicit international significance and well-documented cultural/outdoor places can also qualify. Language variants count as one language, and a generic `landmark=yes` tag does not by itself promote a place to a highlight. Heritage status alone is insufficient. Highlight cards expose their source-evidence reasons on the category badge. This is a metadata heuristic, not a guarantee that every must-see is annotated correctly. Cities with insufficient evidence show an explanation and access to **All places**, rather than arbitrary substitutes.

Both **Highlights** and **All places** show their counts and paginate cards in groups of 40 with Previous/Next controls. This is a display page size rather than a search limit. All places remains a deliberate list choice and does not flood the overview map. The availability filter applies before pagination. Selecting an additional place on the map switches the list to All places, opens its corresponding page and highlights the card. Language changes preserve the list mode, page, event-layer setting and map view. The automatic planner retains its separate bounded candidate search described above.

After the base city catalogue loads, an optional reference check queries [Wikidata's entity API](https://www.mediawiki.org/wiki/Wikibase/API) for the exact `wikidata` identifiers published on mapped places. A place with articles in at least 30 Wikipedia language editions can additionally qualify as a highlight, even if its OSM names are sparsely translated. This conservative heuristic corroborates prominence; it is not a popularity ranking or a guarantee that the place suits every traveller. Existing highlights are never demoted when reference evidence is absent. Names alone cannot establish identity, and the check cannot introduce new objects or coordinates outside the existing city search.

Place cards and map popups link to the matched Wikidata entity and display the Wikipedia language count. Highlight reasons explain this criterion in RU/EN. Wikipedia language variants are deduplicated; Commons, Wikivoyage and other Wikimedia projects do not inflate the count. The first map appears before reference checking completes. The optional stage has a six-second overall request budget, batches up to 50 unique identifiers and runs at most two requests concurrently. Complete reference batches are cached for seven days, partially resolved batches for one hour. Source failures are not cached as empty successful evidence. Missing or mismatched identities leave the original places unchanged; partial and unavailable checks are labelled separately from geographic coverage. Valid reference evidence survives offline restoration. Objects without an exact Wikidata identifier still use the base OSM prominence rules; matching additional tourist sources remains future work.

The map initially shows highlights as individual markers, with name labels where they fit without overlapping each other. Highlights are never hidden inside numeric clusters. The initial camera frames the main visitor area; remote highlights remain in the list and on the map when their area is in view. This camera choice does not change the geographic search scope. Additional documented places appear from zoom 15 and local context from zoom 17. Explicitly selecting any place in the list reveals it immediately with its published hours and source link. Use the mouse wheel to zoom.

The basemap uses [OpenFreeMap](https://openfreemap.org/quick_start/) vector tiles through MapLibre's Leaflet adapter. The RU/EN switch selects published `name:ru` or `name:en` fields. Missing Russian labels retain local Cyrillic names, then use available English or Latin labels before the original script. Legacy `name_en` is also supported. Missing translations can be replaced in the background as described below. Road numbers and other non-name labels are retained. Light mode uses Positron and dark mode uses the provider's native Dark style. Theme changes update the vector style without replacing the Leaflet map or its overlays. Language changes retain the camera and saved plan. Provider, OpenMapTiles and OpenStreetMap attribution remains on the map. Libraries, workers and CSS are served locally; styles, tiles, sprites and glyphs require access to `tiles.openfreemap.org`. No map API key is needed.

If vector initialization, style loading or initial rendering fails, the map falls back to standard OpenStreetMap raster tiles and explicitly identifies their local-language labels. Raster fallback retains the existing dark-mode filter; vector maps use their own palette. Pending style requests, observers and rendering layers are disposed when a workspace closes, so late work cannot attach a map to an abandoned city.

The vector map requires WebGL2. A fallback notice now explains that raster labels cannot be translated and offers a retry button. Initialization is accepted on the first successful map load instead of waiting only for every resource to become idle. Check browser graphics acceleration when the reported reason is `webgl2-unavailable`; a failed tile request alone does not prove that graphics support is missing.

Place names in cards, popups, route markers, proposals and itineraries prefer the requested OSM translation, then an exact-identity Wikidata label. Missing Russian labels use a cached machine translation when available, otherwise a readable local Cyrillic or published English name before the original. The optional Wikidata stage requests only RU/EN labels alongside reference evidence; it verifies the returned entity ID and each label's language. Fresh names also update old saved stops for display, including walking and map labels, without rewriting saved stop coordinates, durations or ordering. Organiser event titles are retained.

Missing labels on the visible vector map and visible place cards are translated through [MyMemory's free API](https://mymemory.translated.net/doc/usagelimits.php), without an account or API key. Only public names and language codes are sent; translation does not delay the initial map or place search. English source labels are preferred; other scripts use automatic language detection. Published translations and local Cyrillic names in Russian mode always take precedence. A map notice and card tooltips identify machine translations, which can mistranslate proper names. Raster tile images cannot be translated by this mechanism.

Visible landmark marker labels and opened place popups also request missing translations, even if the corresponding list card is outside the viewport. Requests for the same popup are shared while a map refreshes. Completed translations update existing marker labels and popup content without closing the selected place. Readable Latin street labels do not consume automatic basemap translation quota, leaving more capacity for visitor places and otherwise unreadable labels.

Anonymous MyMemory usage is limited to 5,000 characters per day. The server reserves a conservative 4,500-character daily budget, shares one bounded queue across city requests, and persists reservations in `.cache/translations`. Successful translations are cached there and in browser storage for 30 days, with bounded cache sizes. Keep that directory to retain the budget across restarts; `PLACE_CACHE_DIR=off` disables disk persistence for tests. The application sends at most four names per request, stops queued work when a city closes, and pauses after upstream failures or quota exhaustion. Available English/Latin/original names stay visible. This prototype has no guarantee of translating every label in a large city; sustained use needs a self-hosted translator or a higher-quota service. Multiple application processes do not share an atomic quota counter.

When no matching settlement polygon exists, the app verifies the selected GeoNames ID and coordinates, then searches within 2 km of that centre. The UI labels this as surroundings and does not invent a boundary link or use the surrounding municipality as the settlement. An empty source result remains visible as an empty neighbourhood; a provider outage remains an error. Confirmed city boundaries continue to search the entire city. Nearby settlement results can be cached and restored offline for the same centre.

Compact cities first use a bounding-box query with Overpass area membership. Widely separated administrative territories, including cities with distant islands, are split into connected boundary components and small tiles. An expensive compact-city query can switch to the same strategy automatically. The full boundary geometry is checked for complete member ways and closed outlines before using it. Tiled searches check marker centres and mapped geometry points against that boundary locally, including holes, without asking Overpass to scan a huge marine area. Geometry output includes relation members; marker centres are calculated from geometry when the provider omits them. All components remain in scope. Tiles nearest the selected city centre load first, with at most three tile requests per job. Query-specific timeouts can subdivide a tile further; successful tiles and subdivision decisions are reused on retry.

Park and garden outlines are included in the same compact query while other categories retain compact centre output. Duplicate centre/geometry records for one OSM object are collapsed in favour of geometry. Overpass's [bounding-box centre](https://wiki.openstreetmap.org/wiki/Overpass_API/Overpass_QL#out) can lie outside a concave or multipart park. For complete closed polygon geometry, discovery keeps an existing centre that lies on the mapped area; otherwise it selects a point inside a horizontal land interval, respecting holes and disconnected parts. Tiled queries use the same calculation. Incomplete or unsupported geometry retains the available source centre rather than inventing missing boundary edges. The marker is a representative location, not a verified entrance. The North Tushino regression fixture retains its actual OSM outline and demonstrates the former centre outside the park. Compatible older catalogues are stale fallback during refresh; refreshed coordinates replace them without deleting saved plans.

Boundary discovery and place queries share provider health information. [Dresel regional replicas](https://ovp.dresel.systems/) are selected automatically using the published geometry in the [Geofabrik extract index](https://download.geofabrik.de/technical.html). A replica must conservatively cover the whole query box, including checks for holes and coverage edges. Tiled cities choose a source for each tile, so a remote island does not force the main city away from its regional source. If coverage cannot be verified, the application uses the global providers: VK Maps, overpass-api.de and [Private.coffee Overpass](https://overpass.private.coffee/). The coverage index is shared and cached for 24 hours; index failures do not block global fallback. Regional extracts are updated daily rather than continuously.

Verified regional sources take precedence over global fallbacks; successful global providers are tried first within the fallback group. Failed providers are skipped for 60 seconds. A heavy query is distinguished from a provider outage: an explicit query timeout, or a transport timeout from a recently successful provider, may request smaller tiles without disabling that provider. Boundary queries allow six server seconds, boundary geometry and tiles eight, compact-city places twenty and local places eight, with three extra seconds for transfer and a 35-second transport budget per query. Long queries use POST. A shared queue allows at most three active requests per endpoint across city jobs; cancellation removes queued requests without consuming a slot or marking the provider unhealthy. Requests identify the application and respect cancellation. A shared background job has a three-minute deadline; the first usable places can be returned much earlier. With no usable results, unavailable sources produce a terminal unavailable state with a retry hint. Unavailable components after a successful tile produce an explicitly incomplete catalogue rather than discarding the loaded places. Incomplete aggregates are kept in memory for at most one minute and are not persisted as complete results.

The browser displays progressive results and checks the shared job every two seconds while `loading` is true. Polling stops when the job finishes, fails or the city workspace closes. A disconnected request cancels an initial search when it has no remaining viewers, including its boundary request. After a progress response, the background job has a six-second lease renewed by polling; leaving the city releases its provider requests when that lease expires. One viewer cancelling cannot cancel another viewer's shared request. Abandoned work does not enter a failure cooldown, and completed tiles remain reusable. This prevents rapidly browsing cities from filling the provider queue with abandoned searches.

Large cities first attempt a small central batch with a seven-second budget, then continue across the whole mapped city. The first batch uses the same membership and geometry rules; it does not limit the final search area or number of places. Enclave loading can run alongside the remaining city query once initial places are available. Main-city, preview and enclave records are merged separately so later batches cannot erase one another or lose territorial provenance.

Loading, coverage and retry status remain visible beside the map regardless of the active discovery tab. Background updates preserve the map view, and an unchanged snapshot does not recreate the map. If an old snapshot contains only enclave places, the first main-city batch reframes the map once. Partial refreshes merge new objects into a saved complete catalogue immediately, retaining its original source timestamp and its complete offline baseline until a complete replacement arrives. Expired server catalogues up to seven days old and compatible previous-version catalogues can be shown immediately as stale while refreshing; source timestamps are preserved. A failed refresh keeps the last usable snapshot. The browser also restores compatible previous-version records and strips any saved loading flag, so offline records cannot restart polling. Local replacement caches remain separate and limited to 2 km. Opening hours retain OpenStreetMap notation.

Place API failures with known source causes are terminal JSON states: `status: "unavailable"` for unavailable providers and `status: "unsupported"` when no matching city boundary exists. These responses use HTTP 200, `Cache-Control: no-store`, a `retryAt` timestamp and `Retry-After`. They omit `places`, so they cannot masquerade as a successful empty catalogue. Invalid inputs still return HTTP 400, and unexpected place-processing errors are logged and return HTTP 500. Source failures are cached for one minute and unmatched boundaries for five minutes. The browser honours cooldowns across language/workspace changes, prevents overlapping loads, and disables the retry button until recovery is allowed. A settlement without a confirmed boundary displays the coverage limitation without silently switching to a radius or repeatedly retrying.

In the **Events** tab, choose Today, Tomorrow or set a trip date in the shared bar. The site reads the individual sessions published in OpenAgenda. A multi-day event appears on each day it overlaps, and a recurring performance appears on its scheduled dates. Times use the destination’s time zone, shown alongside the results. When the city has no known time zone, the agenda uses UTC. Switching languages keeps the selected date.

The daily search starts within 5 km of the city centre and expands to 25 km if it finds no sessions. Cancelled and indefinitely postponed listings are omitted. Sold-out events are labelled. When two publishers list the same title at the same venue and start time, the latest publication takes precedence. A source failure offers a retry, and an incomplete schedule is labelled. Event and venue names follow the publisher’s language. [OpenAgenda public dataset](https://public.opendatasoft.com/explore/dataset/evenements-publics-openagenda/)

Open **Venue calendars and travel guide** to find city calendars. Discovery uses the GeoNames ID in Wikidata, municipal websites, their published visitor links and explicit official tourism references in up to three Wikipedia language editions. It recognizes multiple calendar links and municipal subdomains. It also follows published cultural-directory, theatre, museum and cultural-centre links to find venue programmes. Each starting website is limited to eight pages and two link levels, and shared pages are requested once per discovery. When the directory lacks a municipal website or is unavailable, a fallback resolves the GeoNames ID with Open-Meteo and looks for a matching town article within 5 km in English Wikipedia. It reads that article's Wikidata website claims and rejects conflicting GeoNames associations. There is no list of specially configured cities.

**Events by day** reads JSON-LD Event records, Schema.org event microdata in HTML, dated calendar cards with headings and source links, explicit year-first date/time/venue rows, supported local date tables and supported Nuxt embedded event data. Calendar-card dates use the page's declared language and require an explicit year. News publication dates are not treated as event metadata. Embedded data is parsed without executing publisher scripts. Single-day clock times are retained. Multi-day listings keep their published date range without inventing daily sessions.

The selected trip date is sent to the server. It prioritizes published day/month links and supported GET date filters, including native date/month inputs, offered month/year selections and numeric date widgets with a declared page language. When the requested month is not linked directly, it can follow a published month link that moves closer to it, including across a year boundary. It preserves published field names and filter values, respects offered ranges and resolves relative links against a same-origin HTML base. It does not invent month URLs or submit POST forms. Details with published dates far outside the requested day are skipped with a one-day margin for source time zones and midnight crossings. Unverified detail dates remain eligible for inspection.

Each calendar lookup reads up to 24 pages, three at a time, including at most four listing pages connected by date filters or published navigation. It continues to linked details even when the index already contains events. Dated cards may link to another section on the same site. **City calendars checked** shows source links, page attempts, dated-listing counts, unavailable pages and crawl limits. When date navigation was used, it links to the resulting filtered page. These counts describe the publications read before filtering to the selected day. Missing sources and unreadable dates remain distinct from a confirmed empty programme. Discovery and event results are cached for ten minutes after completion. Pending work is shared even when a refresh is requested. Failed discovery is cached for one minute; refresh and changing the trip date cannot bypass that source cooldown. An unavailable official source produces an explicit unavailable/incomplete JSON state, so the interface distinguishes failed discovery from finding no calendars and does not claim that no events exist. Discovery and event caches are separate; event cache entries are separate for each city and trip date, and retrying explicitly refreshes the city lookup. Coverage still depends on published navigation and supported formats; image-only posters, PDFs and calendars requiring unsupported browser requests are not automatically extracted.

**Venue calendars and travel guide** shows up to 25 OpenAgenda venue calendars. Its search covers current and upcoming programmes, independently of the day you selected. Open a programme or copy its venue-specific iCalendar link for the importer below.

The same panel independently looks up a nearby Wikivoyage guide. When the guide has an events or festivals section, it links to that section and lists the websites cited there, even when OpenAgenda has no calendars. These links are useful for checking dates with organisers. In the Russian interface, the site also checks the English edition when local festival links are missing. [Wikivoyage](https://www.wikivoyage.org/)

The browser saves the calendar references for each city for reuse. Opening a city again after 24 hours rechecks the directory. **Check again** requests an immediate refresh. If the directory is unavailable, the site labels any saved result with its original check time.

### Command line and tests

```sh
node bin/city.mjs "Budapest"
node --test --test-concurrency=1
```

The first command prints a JSON array of matches. Each match includes the provider’s ID, the place name, and its coordinates. The region, country, country code, and time zone are `null` when the provider omits them. Use the ID and region to distinguish places with the same name.

An empty array means the search found no matching settlements. Try another spelling if you expect a match. For example, during testing, `Kyoto` returned results while `京都` returned an empty array. If the request fails, the command writes an error to standard error and exits with a nonzero status.

`node --test` checks city search, daily schedules, calendar and guide discovery, caching and event imports offline.

The Leaflet lifecycle regression additionally runs in headless Chrome when `CHROME_BIN` points to a Chrome or Chromium executable. For example, in PowerShell:

```powershell
$env:CHROME_BIN = 'C:\Program Files\Google\Chrome\Application\chrome.exe'
node --test --test-concurrency=1
```

Browser tests start isolated local servers and block external requests. They check wheel zoom during place updates, immediate map replacement with a pending wheel event, RU/EN vector expressions, theme changes, attribution, camera preservation, an explicitly labelled raster fallback, visible-label translation and saved travel interests. A small local test style exercises MapLibre and its workers without depending on public tile availability. Without `CHROME_BIN`, browser tests are skipped. If Windows blocks automatically assigned ports, set `BROWSER_TEST_PORT` and `BROWSER_DEBUG_PORT` to two free test ports and run with `--test-concurrency=1`. Test processes are stopped afterwards. The application keeps its Leaflet instance when progressive place batches arrive, and explicitly cancels Leaflet 1.9's pending wheel timer before removing a workspace map.

Place names and coordinates come from GeoNames via Open-Meteo. [Geocoding API documentation](https://open-meteo.com/en/docs/geocoding-api) · [GeoNames](https://www.geonames.org/)

### Import an event calendar

Pass the organizer’s direct iCalendar download URL. The importer writes JSON to standard output. These examples use two organizers’ own publications.

```sh
node bin/events.mjs "https://www.stmarysbc.com/events/christmas-fair-2026/ical/"
node bin/events.mjs "https://carlypaoli.com/events/italian-church-concert/?ical=1"
```

The import records the calendar URL and the UTC time it was checked. Each event includes its source UID, title, venue, published start and end, status, and organizer link when available. If an event has no link, its URL points to the calendar. An empty calendar produces an empty event list. Download and parsing errors go to standard error with a nonzero exit status.

Dates and clock times follow the publication. A date-only event has `time: null`, and its end date is exclusive. UTC times retain their UTC label. For local times, the importer uses the event’s time zone, then the calendar’s declared default if present. A floating time with neither has `timezone: null`. An explicit duration is kept when supplied. Each published event definition appears once per entry in the feed. Recurring series and their exceptions are identified for later expansion into a daily agenda.

## Development

The bilingual desktop website comes first. A mobile adaptation is planned for a later stage.

We keep ideas and acceptance criteria in a local `ROADMAP.md` at the repository root. Git ignores this file. We build one end-to-end feature at a time. Once it works through the website or CLI, we document how to use it here and remove the completed item from the roadmap.

We maintain a single application and keep data access separate from presentation. We introduce shared abstractions when multiple parts of the app need them. Cities such as Budapest serve as test cases. The app fetches its data automatically from external sources.
